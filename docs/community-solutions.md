# 社区方案调研：Cloudflare 与登录 Cookie

> 调研时间：2026-11-11。所有结论均来自可核查的源码、官方文档或 Maven 构件，不含经验推测。
> 关联：`docs/cookie-cloudflare.md`（本项目的实现方案）、`docs/architecture.md` ADR-009。

## 0. 结论

社区经验是**按站点防护强度分三级递进**，而不是一个通吃方案。级别越高，代价越大，覆盖的站点越少。

| 级别 | 做法 | 代表实现 | 能解决 | 主要代价 |
|---|---|---|---|---|
| **L1** | WebView 过盾 → 导出 Cookie → 原生 HTTP 复用 | Mihon `CloudflareInterceptor` | 绝大多数 CF 站点 | 浏览器指纹不一致的站点仍失败 |
| **L2** | 请求本身改由 WebView 的 `fetch()` 发出 | keiyoushi `WebViewFetchInterceptor`、Litho WebView 网关 | 连 TLS 指纹也校验的站点 | JS bridge 开销、二进制 base64 膨胀、并发受限 |
| **L3** | 换掉 TLS 栈，使 ClientHello 等同 Chrome | Android `cronet-embedded`、`curl-impersonate` | 纯指纹拦截 | 平台覆盖不全，iOS/桌面无现成解 |

**对本项目的映射**：Android 走 L1 + 可选 L3（Cronet）；iOS 走 L1 + L2 兜底；桌面维持 ADR-009（Cookie 导入 + 可选本地 sidecar），因为 JVM 上 L3 无解。

## 1. L1：WebView 过盾 + Cookie 复用

### 1.1 Mihon 的实现（最完整的开源参考）

`CloudflareInterceptor` 继承 `WebViewInterceptor`，用**隐藏 WebView** 自动过盾。它的工程细节比我们目前的实现更完整，有 5 处值得直接对齐：

| 机制 | Mihon 的做法 | 我们的现状 | 建议 |
|---|---|---|---|
| 检测 | `cf-mitigated` 响应头 + `Server` 头 | 已有 `CloudflareGuard.classify`，判据一致 | ✅ 已对齐 |
| 并发 | **按 host 加锁**，同一域名不并发开窗 | 无 | 需补 |
| 超时 | 12 秒，超时抛 `CloudflareBypassException` | 无 | 需补 |
| JS 执行 | 优先用 **isolated world**，防页面脚本干扰 | 无 | 需补 |
| 身份 | 同步 UA **和 Sec-CH-UA client hints** | 只存了 UA | 需补 client hints |
| 版本 | 要求 Chrome 84+，过旧提示升级 WebView | 无 | 需补 |

host 锁这条不是性能优化，是**正确性问题**：同一域名并发开多个 WebView 会互相冲掉 `cf_clearance`，表现为"过了盾又立刻被挑战"。

### 1.2 为什么 OkHttp 复用 WebView 的 Cookie 通常能工作

这是最反直觉的一点。按 Cloudflare 的三重绑定（IP / UA / TLS），OkHttp 的 TLS 指纹与 WebView 不同，理论上应该必然失败。但 Mihon 有数十万用户在用 L1，说明**TLS 指纹在多数站点是加分项而非硬门槛**。

社区对绑定强度的表述也不一致，需要注意区分措辞：

| 来源 | 对 TLS 绑定的表述 |
|---|---|
| [capskip](https://capskip.com/cf-clearance-cookie) | "**通常**不"（Usually not）—— 握手在 cookie 之前被读取，不匹配会更早被发现 |
| [crawlex](https://blog.crawlex.net/blog/cloudflare-cf-clearance-cookie) | 三者任一不符 → re-challenge；但未给出各维度的权重 |
| [Cloudflare 官方](https://cloudflare-docs.justalittlebyte.ovh/turnstile/get-started/mobile-implementation) | "clearance 只在**相同环境**被接受，包括相同的浏览器与设备配置" |

**结论：绑定强度是按站点配置的，不是全局常量。** 所以正确的架构是**分级降级**——L1 失败后自动升级到 L2，而不是一开始就上最重的方案。

### 1.3 一个必须接受的现实

[keiyoushi PR #11886](https://onlybits.org/keiyoushi/extensions-source/pull/11886) 的 reviewer 指出：某些站点会拒绝 WebView 自动附加的 `X-Requested-With` 等头，导致**在 WebView 里就过不了盾**，后面自然拿不到 clearance。这类站点在 L1 和 L2 下都无解。

## 2. L2：让 WebView 自己发请求

### 2.1 keiyoushi `WebViewFetchInterceptor`（PR #11886，2025-11-30）

这是社区对"OkHttp 指纹不同"最直接的回应。它的自我说明写得很清楚：

> Cloudflare Turnstile can detect and block requests from OkHttp3 clients because it performs TLS/SSL fingerprinting. The TLS/SSL signatures generated by OkHttp3 are different from those generated by a real browser (WebView).

实现方式：拦截 OkHttp 请求 → 在 WebView 上下文中执行 JS `fetch()` → 响应 **base64 编码**后经 JavaScriptInterface 回传 → 构造 `OkHttp Response` 返回。

关键设计点：
- 默认用**请求自身的域名**作为 WebView 的 base URL，无需显式 `loadUrl`
- 支持 GET/POST + body，保留全部请求头（含 UA）
- 提供 `filter` 谓词，只拦截需要过盾的域名
- 默认 60 秒超时

### 2.2 Litho 的「WebView 网关」（iOS 独立实现）

[Litho](https://www.cassianflorin.com/zh/litho) 是 linux.do 的第三方移动客户端，它的地基就是同一思路，且在文章里给出了对照实测：

```
WebView 网关 fetch()  → 200 OK
裸 curl / URLSession → 403  cf-mitigated: challenge（同一网络下）
```

它还解决了两个工程问题，值得抄：

1. **图片也走网关**：在页面里 `fetch` 二进制 → base64 回传 → 交给原生图片加载器。否则图片请求仍会因指纹不符被拦。
2. **挑战自愈**：偶发撞盾时网关自动重载页面重新过盾，无需重启 App。

### 2.3 代价清单（必须先接受再决定）

| 代价 | 量化 |
|---|---|
| 二进制膨胀 | base64 编码使图片/字体体积 +33% |
| 大 JSON 延迟 | 字符串跨 JS↔Native 边界，MB 级 JSON 明显变慢 |
| 并发 | 单 WebView 上下文串行，多请求需排队或多开窗 |
| 长轮询 | MessageBus / SSE 类通道需自己实现 |
| 内存 | WebView 常驻 + 大响应字符串，低端机压力大 |
| 头污染 | WebView 自动附加 `X-Requested-With`、`Sec-Fetch-*`，部分站点拒绝 |

**判断**：漫画阅读器的主要流量是**图片**，而图片本来就可以直接由 `<img>` 或原生加载器发出。所以 L2 只需要覆盖**API 的 JSON 请求**（搜索、详情、章节列表），不需要覆盖图片流。这大幅降低了 L2 的成本——单次搜索的 JSON 只有几十 KB。

## 3. L3：改 TLS 栈

### 3.1 Android：Cronet 是唯一现成解

`org.chromium.net:cronet-embedded` 在 Google Maven 上有正式发布，实测 `maven-metadata.xml` 返回 200，最新版本：

```
143.7445.0   （另有 500.0.1 / 500.0.2 / 500.1.0 系列）
```

Cronet 复用 Chromium 完整网络栈（BoringSSL + HTTP/2 + QUIC），**JA3/JA4 与同版本 Chrome 一致**，不是"模拟"而是"同源"。接入方式相当于替换 OkHttp 的底层，保留 OkHttp 的拦截器链（`CronetInterceptor` 模式）。

代价：APK 增大约 8–15 MB（按 ABI 拆分可缓解），且 Cronet 版本与 Chrome 版本绑定，需跟随升级。

> 注意：网上大量文章说要"自己拉 Chromium 源码编译 30–60 分钟"。那是为了**自定义指纹参数**。如果只需要"和官方 Chrome 一致"，直接用 Maven 上的 `cronet-embedded` 即可，不必自编。

### 3.2 iOS：不可改，只能换传输层

iOS 上 TLS 由系统栈提供（`URLSession` → Network.framework），**应用层无法修改 ClientHello**。三条路都不通：

| 方案 | 可行性 |
|---|---|
| 自定义 BoringSSL + 裸 socket | 理论可行，工程量为月级，且要自己实现 HTTP/2 |
| Cronet for iOS | Google 未公开发布，需自编 Chromium |
| 换传输层 | ✅ 即 L2（WKWebView 的 `fetch`） |

**所以 iOS 上 L2 不是可选项，是唯一解。** 这也解释了为什么 Litho 在 iOS 上直接把整个网络层做成 WebView 网关。

### 3.3 JVM Desktop：无解（实测确认）

| 候选 | 实测结果 |
|---|---|
| `ktor-client-curl` | `-jvm` / `-android` / `-iosarm64` 变体**全部 404**，只发布 linux/macos/mingw |
| `ktor-impersonate` | Maven Central **404**，README 自述 "not ready for usage"，仅支持 Android |
| `curl-impersonate` 的 JNI 封装 | 需自行编译 `.so` 并写 JNA/JNI 绑定，无成熟 KMP 库 |

这直接支持 ADR-009 的结论：**桌面端不做内嵌浏览器**。不是因为内嵌无效，而是三条 L3 路都堵死，而 L1/L2 在桌面都要背一个 Chromium（KCEF 200 MB + jogamp 不可达）。

## 4. 桌面端：sidecar 路线

如果桌面端以后真需要过盾，社区的做法不是内嵌，而是**外挂一个本地求解服务**：

| 项目 | 状态 | 说明 |
|---|---|---|
| FlareSolverr | **已 archived** | 只认旧版 IUAM 挑战，遇 Turnstile / managed challenge 直接返回挑战页 |
| [Byparr](https://bytesized-hosting.com/guides/flaresolverr-on-a-seedbox-cloudflare-bypass-for-indexers) | 活跃 | FlareSolverr 的 drop-in 替代，同 JSON API、同端口协议 |
| [TRAWL](https://hysenlabs.com/projects/germondai-trawl) | 活跃（2026-11 仍有提交） | 提供 **forward proxy** 而非仅 cookie 回传 |
| [flaresolverr-rs](https://lib.rs/crates/flaresolverr-rs) | 活跃 | Rust 实现，自带 stealth 浏览器，benchmark 称 20/20 通过、p50 3.0s |

**TRAWL 的 README 指出了最关键的一点**，与本项目独立得出的结论完全一致：

> Prowlarr keeps only the cookie and user-agent and re-fetches the page with its own HTTP client, so the cookie is not portable and the page gets re-challenged.

也就是说，**"求解器给 cookie、客户端自己重发"这条路本身就有结构性缺陷**。TRAWL 的解法是提供真正的 HTTP/HTTPS 正向代理，让客户端所有请求都从浏览器会话走——本质上是把 L2 的"换传输层"做成了进程外服务。

对桌面端的启示：如果要做，**不要做 cookie 中转，要做 forward proxy**。但这需要生成 CA 证书并让用户装进系统信任库，对普通用户门槛过高，只能作为高级选项。

## 5. 对 Kurisa 的落地建议

### 5.1 分平台矩阵

| 平台 | 主路径 | 兜底 | 不做 |
|---|---|---|---|
| **Android** | L1（Mihon 式隐藏 WebView + host 锁） | L2（`WebView.fetch`，仅 JSON API） | 默认不启 Cronet，作为"高防源"开关 |
| **iOS** | L1（WKWebView + `WKHTTPCookieStore.allCookies`） | L2（必须，因 TLS 不可改） | 不尝试改 TLS |
| **Desktop** | Cookie 导入（现有方案） | 可选 sidecar（Byparr/TRAWL），默认关闭 | 不内嵌浏览器（ADR-009） |

### 5.2 三条需要修正的既有认知

1. **Venera 桌面端是内嵌 WebView 的。** 它用 `AppWebview` / `DesktopWebview` 双实现，登录后自动同步 Cookie。所以 ADR-009 的"桌面不内嵌"是**成本选择**（KCEF 200 MB + jogamp 不可达），不是"内嵌无效"的判断，文档措辞需要区分，否则读者会误以为技术上做不到。

2. **Ktor 的 Curl 引擎不覆盖 JVM。** 它只支持 linuxX64/linuxArm64/macosX64/macosArm64/mingwX64。桌面是 JVM target，本来就用不了。架构文档定 CIO 是对的，但理由要写对——不是"CIO 更好"，而是"Curl 在 JVM 上不存在"。

3. **cf_clearance 的 TLS 绑定是站点级配置，不是全局常量。** 这决定了架构必须是"L1 失败后自动升级 L2"，而不是在编译期二选一。

### 5.3 最自然的落点

项目已经把网络层抽象成了 `SourceHttp` 接口（`commonMain`），这意味着 **L2 不需要改任何业务代码**，只要再加一个实现：

```kotlin
// 现有
interface SourceHttp {
    suspend fun fetch(method: String, url: String, headers: Map<String, String>, body: String?): SourceHttpResponse
}

// L2 新增（实现方式：Android 用 evaluateJavascript + base64；iOS 用 WKWebView fetch）
class WebViewFetchHttp(private val webView: PlatformWebView) : SourceHttp { ... }
```

配合 `CloudflareGuard` 已有的分类结果做路由：

```
请求 → 200                    → 返回
     → cf-mitigated: challenge → L1 过盾 → 重试
     → 仍失败（TLS 指纹）       → 切 L2 重试
     → WAF 阻断（1020）        → 直接报错，不重试
```
